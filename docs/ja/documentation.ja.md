# 文書の配置・翻訳方針

[English](../documentation.md) · [日本語の目次](README.md)

英語をOSSの公開上の第一言語とし、日本語でも同じ機能を理解・利用できるようにします。サイトの入口は`/en/`、日本語は`/ja/`です。言語を切り替えても同じページへ移動できる構成を維持します。

## 配置する場所

| 内容 | 英語 | 日本語 |
| --- | --- | --- |
| プロジェクト概要と最短の導入 | ルートの`README.md` | 日本語サイトへのリンク |
| 導入、操作ガイド、基本リファレンス | `website/src/content/docs/en/` | `website/src/content/docs/ja/`の同じ相対パス |
| サイトを補う詳細仕様・開発手順 | `docs/<name>.md` | `docs/ja/<name>.ja.md` |
| 製品仕様とアーキテクチャ | `docs/SPEC.md`、`docs/ARCHITECTURE.md` | `docs/ja/SPEC.ja.md`、`docs/ja/ARCHITECTURE.ja.md` |
| 補足の目次 | `docs/README.md` | `docs/ja/README.md` |
| サイトの開発・CI・Pages設定 | `website/README.md` | この方針から参照 |

`docs/en/`は作りません。サイトの原稿はStarlight側にだけ置き、補足から該当ガイドへリンクします。補足にはガイドを繰り返さず、値域・境界条件・手動セットアップ・実装契約などを記載します。補足をサイトへ移したときは、その日英本文を補足から削除し、関連リンクを更新してください。

日英対応の対象は公開サイトと目次に載せた文書で、[SPEC](SPEC.ja.md)と[ARCHITECTURE](ARCHITECTURE.ja.md)も含みます。利用ガイドを重複させず、契約と実装境界を両言語で維持します。両言語に共通の英語見出しアンカーを設け、既存リンク用の旧日本語アンカーも保持します。調査・ADR・Agent運用文書は別の用途を持ち、この日英対応の対象外です。過去の調査記録を現行の利用ガイドとして扱いません。

## 更新の手順

1. CLI実装とSPECを読み、変更する事実と、その説明を所有するサイトページまたは補足を決めます。
2. 日本語で内容を検討・執筆して構いません。対応する英語版を作成し、同じPRで提出します。英語版だけに機能や注意事項を追加しません。
3. title・description・制約・リンク先の意味を両言語で照合します。コード、JSON field、コマンド名は翻訳せず、実行可能なコード例を一致させます。
4. 補足の追加・削除時は両言語の目次と`website/scripts/check-repository-docs.mjs`の対応表を更新します。見出しの参照先を変えた場合はリポジトリ内のリンクも直します。
5. [サイトの検証手順](../../website/README.md)に従い、Bunによる全検証と日英の画面確認を行います。翻訳の意味は機械的な対応検査とは別にレビューします。

CLI入力・出力を変える場合は、それを説明しているサイトと補足の日英版を同時に更新します。共通契約の変更ではSPEC・ARCHITECTUREも更新します。文書だけの変更ではCLIの動作検証を代替・実施済みと記録せず、リンク・仕様・サイトの確認結果を記録します。

## 公開

Bunの版、依存lockfile、サイト設定は`website/`で管理します。PRでは検証し、`develop`への反映後に同じパイプラインでGitHub Pagesへ公開します。`docs/`の補足はGitHubで閲覧する文書であり、サイトへの自動取り込みは行いません。初回公開の状態と設定手順は[website/README.md](../../website/README.md)を参照してください。
